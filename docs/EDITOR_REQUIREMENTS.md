# 향후 게시판 HTML 편집기 요구사항

이번 UI 배포에는 게시판과 편집기를 추가하지 않는다.

현재 FAQ는 `index.html`의 `faqList`가 공식 원문이며 `node scripts/build-faq.cjs`가 독립 `faq.html`을 만든다. 별도의 FAQ 관리자 편집 API/DB는 없다. 원문 11개 및 4/4/3 구성은 유지한다. FAQ HTML 수정·삭제 검증은 격리된 임시 복제에서 수행하며 운영 문답을 변경하지 않는다.

향후 게시판은 다음을 저장 계층부터 실제 게시 화면까지 검증해야 한다.

- HTML 형식 작성·수정, HTML 소스 보기 및 편집.
- 본문 전체 삭제, 선택 문단과 이미지 삭제, 기존 콘텐츠 전체 교체.
- 삭제와 빈 본문을 명시적 수정으로 처리한다. 빈 값에 이전 내용을 fallback하거나 `value || oldValue`로 복원하지 않는다.
- DB·API·편집기·게시 화면에 같은 저장 버전과 HTML이 반영돼야 한다. 서버 승인 후 캐시/상태를 갱신하고 이전 응답이 새 수정을 덮지 않도록 한다.
- 저장·새로고침·재진입·브라우저 뒤로가기 후 삭제한 콘텐츠가 다시 나타나지 않아야 한다.
- HTML 편집 권한과 서버 저장 검증을 적용하고 게시 시 안전한 HTML만 허용한다. 미리보기와 게시 화면은 같은 정제 규칙을 사용한다.
- 부분 삭제, 전체 삭제, 이미지 삭제, 전체 교체, 동시 수정 충돌, 저장 실패/재시도를 통합 테스트한다. DB 저장 HTML과 API 조회 HTML 및 실제 게시 화면을 각각 비교한다.

설치 상태 보강의 API 근거: [Chrome Get Installed Related Apps](https://developer.chrome.com/docs/capabilities/get-installed-related-apps). 지원하는 브라우저에서 확인 가능한 현재 서비스의 설치 결과만 사용한다. iOS 일반 브라우저에서는 설치 여부를 추측하지 않으며 standalone 신호와 저장된 설치/다시 보지 않기 상태를 사용한다.

## 공지사항 공통 운영 기준

- 기존 `notice/index.html` 목록과 공지별 독립 상세 페이지 구조를 재사용한다. 이미 구현된 기능을 중복 개발하지 않는다.
- 신규 공지는 실제 정식 배포일을 게시일로 확정하고, 최신 날짜순으로 목록 상단에 추가한다. 배포 전에는 임의의 게시일을 확정하지 않는다.
- 공지마다 `/notice/<고유 경로>/` 형태의 독립 URL을 부여한다. 기존 공지 내용과 독립 URL은 유지한다.
- 기존 공지사항 디자인·메뉴·목록 및 상세 페이지 연결 방식을 유지한다. 새로운 배지, 분류명, 디자인을 임의로 추가하지 않는다.
- 정식 배포 시 신규 공지의 독립 URL을 `sitemap.xml`에 추가한다. 실제 배포일·공지 목록·상세 페이지의 게시일이 일치하는지 확인한다.
- 기능 업데이트, 주유소 정보 갱신, 운영 안내, 약관 변경에도 동일한 구조를 사용한다.
- 현재 GPS 공지의 목록 연결은 `/notice/current-location/`, 상세 HTML은 `notice/current-location/index.html`, 원문은 `content/notices/current-location.md`이다. 게시일은 `2026.11.26`으로 확정했으며 신규 URL의 사이트맵 등록은 최종 정식 배포 시 진행한다.
- 이 운영 기준 반영만으로 커밋·Push·정식 배포를 진행하지 않는다. 운영자의 해당 작업 배포 승인을 별도로 확인한다.
- 공지 목록은 기존 전체 FAQ의 `.faq-item`·`.faq-answer` 스타일과 `assets/faq-accordion.js`를 재사용한 아코디언으로 운영한다. 제목·게시일은 항상 보이고, 최신순으로 배치하며 가장 최근 글만 기본 펼침 상태로 둔다.
- 모든 공지는 같은 `details` 그룹 이름을 사용하여 한 항목만 펼친다. 다른 제목을 누르면 이전 글은 접히며, 열린 제목을 다시 누르면 접힌다. 향후 공지에도 같은 구조를 적용하고 FAQ 자체의 코드와 문답은 변경하지 않는다.
- 공지 전문은 목록 페이지의 HTML 안에 보존하여 펼친 자리에서 모두 읽을 수 있게 한다. 독립 상세 URL도 유지한다. 현재 GPS 공지는 `/notice/current-location/`, 기존 오픈 공지는 `/updates/`로 연결하며 하단 서비스 운영 안내 1~4번은 별도로 그대로 보존한다.

## 안내 문서 원문 보존 및 실제 표시 확인

- 공지 운영 안내의 승인 원문은 `content/notice.md`, 정보 출처 및 갱신 기준의 승인 원문은 `content/sources.md`에 전체 보존한다. 두 파일은 운영자가 직접 제공한 최종 원문이며 일부 문단만 추출하거나 요약하지 않는다.
- 현재 `/notice/`, `/sources/`, `/terms/`, `/privacy/`는 각 `index.html`의 `#pageBody` 정적 HTML을 표시한다. 공지·출처 HTML은 승인 Markdown의 전체 내용과 링크를 같은 순서로 반영한 미러로 관리한다. HTML만 수정한 뒤 원본을 방치하거나, 비어 있는 Markdown으로 연결하지 않는다.
- `assets/info-pages.js`의 `loadManuscript`는 `data-markdown` 연결과 상태 표시 요소가 있을 때만 실행된다. 수정 전 해당 페이지의 실제 연결 여부, 원본 경로, 전체 내용, HTML 대체 동작을 먼저 확인한다. 로딩하지 않는 원본을 실제 표시 원본으로 오인하지 않는다.
- 수정 전 전체 원문과 현재 작업본을 백업하고, 수정 후에는 번호·문단·링크·강조·메뉴 및 실제 HTTP 응답을 대조한다. 일부 문구가 HTML에 존재한다는 확인만으로 완료 처리하지 않는다. 원문을 찾지 못한 부분은 임의 작성하지 않고 보고한다.
- 개인정보처리방침과 이용약관은 GPS 추가 직전 최신 배포본을 비교 기준으로 삼되, 최신 승인된 보관·파기·국외 이전·문의처 및 GPS 문구를 과거 버전으로 되돌리지 않는다.
- 전체 FAQ의 원문은 `index.html`의 `faqList`이고 표시 파일은 `faq.html`이다. `/faq` 운영 URL과 SEO 구조를 유지한다. 8801 정적 미리보기에서는 `.local-backups/preview-server.py`가 `/faq`를 같은 `faq.html`로 처리하며, 이 로컬 전용 서버 파일은 배포 대상에서 제외한다.
- 화면 검증을 하지 않은 경우 HTTP·원본 일치 검사와 실제 화면 검증을 구분하여 보고한다. 게시일·개정 시행일 확정 및 신규 공지 사이트맵 반영은 승인된 정식 배포 시 진행한다.

## 업데이트 내역 고정 운영 기준

- 메인 화면 ‘한눈에 보기’의 업데이트 팝업에는 최신 업데이트 1건만 표시한다. 기존 카드·팝업 디자인과 ‘전체 안내 페이지 보기’ 연결을 유지하며 과거 기록을 누적 표시하지 않는다.
- `/updates/`에는 최신순으로 기록을 누적한다. 최신 항목만 기본 펼침이며, 제목·날짜는 항상 표시한다. 기존 Q&A·공지사항의 아코디언 디자인과 단일 항목 펼침·재클릭 접힘 방식을 재사용한다.
- 신규 기능, 주요 정보 갱신, 시민 의견 반영을 중심으로 기록한다. 사소한 디자인 변경이나 내부 전산 작업을 별도 업데이트로 공개하지 않는다.
- 기존 업데이트 기록을 삭제하거나 임의로 변경하지 않는다. 기존 오픈 기록의 `/updates/` URL과 `#update-open-title` 연결을 유지한다.
- 메인 팝업의 `assets/resource-popups.js` 업데이트 본문과 `updates/index.html`의 최신 제목·날짜·전문·최종 확인일을 동일하게 유지한다. 한쪽만 수정하지 않는다.
- 오늘 업데이트를 공지사항에 중복 등록하지 않으며 기존 공지사항 운영 기준은 유지한다. 최종 확인일의 공통 설정은 `ui-config.js`의 `checkedDate`를 사용하고, 명시적으로 승인된 변경 자료 없이 주유소별 상태나 좌표를 변경하지 않는다.
- 이번 작업 이후 별도 지시 전 신규 기능 개발을 진행하지 않는다. 운영자 관리·Gmail 연동과 전체 백업·보안 정리는 이번 업데이트 범위에 포함하지 않는다.
